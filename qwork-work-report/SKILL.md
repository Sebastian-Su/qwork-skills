# QWork 工作日志

先取证并生成草稿；用户明确确认后才发布。不要把生成草稿与发布合并为同一步。

## 1. 确定口径

1. 直接根据提示确定报告类型和时间范围，不要先向用户追问：
   - 未提供任何日期、星期或时间范围时，直接生成当前自然日的日报。
   - 指定一个日期或某一天时，生成该自然日的日报。
   - 明确说“周报”“本周”或“一周”时，生成当前周一至当前日的周报；明确说“上周”时，生成上一自然周的周报。
   - 指定完整一周或连续日期区间时，生成该范围的周报；用户给出的起止日期优先。
   - 只有日期表达互相冲突且无法从上下文消解时才询问；不得仅因用户没有写“日报”或“周报”而询问。
2. 确认范围是个人工作、团队工作还是指定项目。未明确时，按 QWork 项目路径图统计，不得把“当前项目”等同于当前 cwd。
3. 默认受众是领导和项目组成员：他们关心交付成果、关键数字、项目推进和需要协调的关键事项，不需要阅读内部排查流水、完整红项清单或测试术语堆叠。用户明确指定技术团队、评审人或其他受众时再切换表达深度。
4. 将时间、仓库、分支和证据范围写在内部取证笔记中，不要默认塞进最终短报告。

## 2. 收集证据

开始取证前先建立“QWork 项目路径图”，然后逐路径扫描，不得只扫描当前仓库目录：

1. 始终纳入当前 qwork 仓库、该仓库的 linked worktree，以及时间窗口内由 QWork 工作明确派生的相邻仓库。
2. 已知相关根包括 `/Users/suzhou/Documents/WorkSpace/360/Tools/workbuddy-analysis` 和 `/Users/suzhou/Documents/WorkSpace/360/qwork/ziqdo-bench`。路径存在或原始会话证明该时段在其中工作时，即使 session 直接从该目录启动，也必须纳入。
3. 从 Codex/Claude 会话的 `cwd`、命令 `workdir`、文件链接、Git 根目录、计划和报告继续发现其他相关路径。只有目标、代码或产物明确属于 QWork 工作时才加入，避免把同一用户的无关项目混入。
4. 在内部取证笔记记录“路径 → 与 QWork 的关系 → 命中的会话/Git/测试证据”。某个相关路径无法读取时，把它记为证据缺口，不得当作零工作量。
5. 扫描路径图中所有时间窗口内的 Codex 活跃与归档 session、Claude Code project session；跨日 session 只计算窗口内发生的活动。主会话、续接、Fork、研究子会话可作为证据，但 Guardian、审批和纯辅助会话不单独计工时。

优先读取原始证据，顺序如下：

1. 项目路径图中相关的 Codex 与 Claude Code 用户会话正文，而不只是会话标题或数量。
2. 每个相关 Git 仓库在时间窗口内的所有相关分支提交、作者、提交说明和变更统计；同时检查当前分支、远端位置和工作树状态。
3. 测试命令、报告、截图、trace、真实运行记录和文档回读结果。
4. 项目计划、规格、调研报告、培训材料和用户提供的补充说明。
5. 保持仓库归属：`workbuddy-analysis`、`ziqdo-bench` 等工作计入 QWork 工作日志，但不得写成 qwork 仓库代码或提交。
6. 生成周报时额外提取：本周工作方式发生的变化、个人能力成长、重复阻塞、流程改进建议，以及下周可验证的新 AI 协作实验。
7. 为明日或下周建议读取可用的用户/项目记忆、当前计划与产品技术路径；易变化的事实应从当前仓库或权威一手来源重新核对，不把旧记忆当作当前事实。

会话只能说明做过什么，Git 只能说明落了什么，测试和运行证据才能说明达到什么状态。三者冲突时采用更保守的结论。

## 3. 合并与判定

- 按“目标/项目”合并主会话、续接会话、Fork 和内部辅助会话，不按会话数量罗列流水账。
- 将调研、实现、测试、修复和报告视为同一目标的不同阶段；只有可独立验收的成果才拆成单独事项。
- 区分 `已调研`、`已实现`、`目标测试通过`、`已进入 develop`、`全量门禁通过`、`已发布`。不得相互替代。
- 随机抽样、局部测试、fake sidecar、单次模型冒烟和报告中的自述都不能扩大成全产品结论。
- 保留改变决策的数字，如测试通过率、失败数、真实包数量、分支状态和外部阻塞；删除不影响判断的命令流水。
- 将“真实性判定”和“对外表达”分开：内部必须完整记录失败、阻塞和证据边界；对领导/项目组的报告只保留会改变完成判断、资源协调或后续安排的限制，不展开低层技术红项。
- 不用未完成项冲淡当日已完成成果。某项工作已完成其承诺范围时，直接写成果；不得因为全产品仍有其他问题就在每一条后面追加免责声明。
- 工时仅在用户要求时估算。根据有效活动、提交和产物估算，同一目标的并行会话不重复计时，并明确“非考勤精确计时”。
- 将事实、个人反思和下周设想分开：反思必须能追溯到本周经历，设想要写明准备在哪个环节尝试什么新方式，以及如何判断是否有效；不得虚构个人感受或已执行结果。

## 4. 生成草稿

完整读取 [references/report-template.md](references/report-template.md)，选择日报或周报模板；需要引导用户修改或选择后续尝试时，完整读取 [references/interaction-guide.md](references/interaction-guide.md)。

写作要求：

- 默认生成“管理层成果版”：让不了解实现细节的人一眼看到今天交付了什么、结果有多确定、项目推进到了哪里。
- 使用自然、凝练、像本人写完后经过专业润色的中文；语气稳健，不写营销口号，不使用 AI 腔。
- 每项采用“动作 + 对象 + 结果”的完整句式。优先使用“完成、修复、打通、建立、验证、提交、发布”等明确动词，结果紧跟其后。
- 把同一目标的实现、测试、报告和提交合并为一项，不把过程拆成流水账。日报通常保留 4—7 项，每项控制在一到两句。
- 关键数字只保留能证明规模、质量或阶段推进的部分；多个同类测试数字合并表达，不连续堆砌文件名、哈希、路径和内部状态词。
- 首次出现的英文门禁或技术概念用中文解释，确有必要时再在括号中保留英文；避免一段中密集出现 `test-ready`、`not_evaluated` 等内部术语。
- 默认使用清爽的 Markdown：加粗标题和栏目名、编号成果项、统一中文标点；修正重复句号、断句不顺和中英文空格问题。
- `产出文档`、`工作总结`、`未完成项` 和 `明日尝试` 保持为完整日报的固定栏目。`工作总结` 通常一段，只概括主线和阶段变化，不重复“今日工作”。
- `未完成项` 保留，但面向领导和项目组压缩为一到两句，只概括主要后续事项；普通技术债、局部红项、未运行命令和内部修复细节留在取证笔记，不默认展开。
- 用户只修改或重写某一栏目时，只更新该栏目，其他栏目必须原样保留；不得把局部修改理解为删除其他栏目。只有用户明确说“删除/不需要某栏目”时才能移除。
- 即使压缩限制，也不得把“局部验证”写成“正式发布”，不得把“已授权/执行中”写成“已完成”，不得隐去会直接改变成果真实性的事实。
- 产出文档使用“项目归属 + 项目内相对路径”的展示规则：
  - 文件位于 QWork 项目路径图中的某个 Git/项目根目录内时，以该根目录为基准生成不含 `..` 的相对 Markdown 链接，并用项目标识区分归属，例如 `[qwork] [实施报告](docs/report.md)`、`[workbuddy-analysis] [评测方案](docs/evaluation.md)`。
  - 文件不属于路径图中的任何项目根目录时，只写项目标识和准确标题，不生成本地文件链接。
  - 飞书文档、极库云 MR 等可共享的远程稳定链接可以正常使用。
  - 最终报告不得出现 `/Users/...`、`/private/tmp/...`、worktree 路径、`file://`、`~` 或其他本机绝对路径；绝对路径只允许存在于内部取证笔记。
- 默认不在草稿阶段创建或更新飞书文档，也不发送推推消息。

周报还必须包含以下四节：

1. `本周核心产出`：100—200 个中文字符，只保留最重要的业务/工程成果、决定性指标和阶段变化，不重复罗列全部工作。
2. `本周关键收获：新范式下的成长`：写清从“AI 辅助执行”到需求定义、并行协作、独立验证或证据交付等方面的真实成长。
3. `遇到的问题与对 AI Native 流程的建议`：先写实际问题，再给对应流程建议；建议必须可执行，避免泛泛而谈。
4. `下周更大胆的 AI 协作尝试`：明确选择一个具体环节，尝试一种此前未使用的协作方式，并给出最小验收信号。

补充已经发布的周报时，先只读拉取原帖并核对作者、时间、内容与 `post_id`。若发布工具没有编辑能力，则生成只包含新增栏目、不重复原周报的回帖草稿；仍须展示草稿并等待用户确认后再回帖。

完成草稿后，展示全文，并按交互指南同时给出明日或下周尝试选项。用户已有明确选择或明确不需要计划时，不强行追加选项；用户只提供某一栏的成稿时，仍须保留完整报告的其他栏目。草稿阶段不调用任何外部写入工具。

## 5. 有限交互校准

- 一次只提出一个合并决策问题，同时给出推荐答案；事实能够从环境取证时自行查找，不向用户提问。
- 默认最多主动进行两轮：第一轮校准报告内容并选择后续尝试，第二轮展示合并修改后的完整稿。两轮后只等待修改指令或提交确认，不再主动开启新问题。
- 每轮提供不超过 3 个候选，并允许用户选择“不添加”或直接改写；不要逐段盘问，不要求用户重复已经提供的信息。
- 用户选择候选或提出修改后，更新报告并重新展示受影响内容；涉及多处改动时重新展示全文，避免确认错版本。
- 用户说“确认提交”“确认发布”“可以发”“确认回帖”等明确提交语句时，立即进入发布，不再追问、不再提供新选项。

## 6. 等待确认并发布

只有用户在看到当前草稿后明确说“确认提交”“确认发布”“可以发”“发布到推推”或“确认回帖”等，才进入发布阶段。修改意见不等于发布确认；修改后必须再次展示最终稿并等待确认。明确确认后直接执行，不再追加问题。

确认后：

1. 使用 `tuitui-cli` Skill，完整遵循其成功判定和大数 ID 规则。
2. 默认目标为 `创新业务项目组` 的 `工作日报` 频道；用户指定其他目标时覆盖默认值。
3. 每次发布前重新通过团队名查询频道，取得准确 `channel_id`，不要复用记忆中的 ID。
4. 使用 `teams post send` 发布最终稿。
5. 仅当返回 `errcode === "0"` 时报告成功，并返回 `post_id`；失败时返回原始 `errmsg`，不得声称已发布。
6. 发布后不自动修改草稿、追加飞书文档或转发其他频道，除非用户另有要求。

若是补充既有周报且只能回帖，使用原帖 `post_id` 作为 `--reply`；只有回帖返回 `errcode === "0"` 才报告补充成功，并返回新的回复 `post_id`。

## 7. 完成检查

- 日期范围、日报/周报标题和“今日/本周”用词一致。
- 内部取证笔记已列出完整项目路径图；存在 `workbuddy-analysis`、`ziqdo-bench` 或其他相关路径证据时，没有因其 cwd 不在 qwork 下而漏掉。
- 每个完成结论都有会话、Git、测试、运行或文档证据之一支撑。
- 同一目标没有因多会话、多 Agent 或多次重试重复计算。
- 周报包含四个复盘栏目，且核心产出为 100—200 个中文字符。
- 下周大胆尝试写明具体环节、新协作方式和最小验收信号。
- 需要交互校准时，日报或周报已提供不超过 3 个明日/下周候选，候选来自当前工作、记忆、产品技术路径或可靠的新理念，并包含选择理由与最小验收信号；用户已有明确选择或明确不需要计划时可省略。
- 用户只修改某一栏目时，已核对其余栏目未被删除、缩写或重写。
- 主动交互不超过两轮；用户明确确认提交后没有继续反问。
- 目标范围通过与全产品发布就绪已明确区分。
- 最终报告中的本地文档链接均为所属项目根目录内的相对路径，不含 `..`；项目外文件只显示标题，且全文不包含本机绝对路径、worktree 路径或临时目录。
- 草稿阶段没有发生任何外部发布。
- 发布阶段有用户在当前草稿之后给出的明确确认，以及 `errcode === "0"` 的返回证据。
