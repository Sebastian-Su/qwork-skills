# 报告交互校准指南

## 目标

用最少问题帮助用户纠正事实、调整表达，并选定一个值得尝试的明日或下周行动。借鉴 grilling 的“一次只解决一个决策、事实自行取证、提供推荐答案”，但禁止无上限追问。

## 交互流程

1. 先展示面向领导和项目组的成果版完整草稿，不用问题代替草稿；详细取证边界保留在内部，不默认展开成红项清单。
2. 草稿后列出 3 个候选，并标记 1 个推荐项：
   - **A. 收口型**：直接处理当前最关键的未完成项或外部阻塞。
   - **B. 协作创新型**：尝试此前未使用的 AI 分工、评审、验证或自动化方式。
   - **C. 产品/技术探索型**：沿当前产品路径验证一个新能力、新理念或架构假设。
3. 每个候选只写三件事：具体环节与动作、为什么适合现在、最小验收信号。不要给抽象口号。
4. 只问一个合并问题：`推荐 A。你想采用 A/B/C、保持草稿，还是直接修改某段？` 用户已有明确选择或明确不需要计划时，不强行追加候选；用户只提供某一栏的成稿时，仅替换该栏，其他栏目原样保留。
5. 用户选择后合并进报告，展示更新后的完整版本；如仍有明显的主观取舍，可再问一轮，否则等待提交确认。
6. 默认最多主动两轮。用户继续给修改意见时照做，但不要主动扩展新的问题树。

## 候选依据

按以下顺序选择依据：

1. 本期已完成工作与 `未完成项`；
2. 当前项目计划、PRD、Git 分支与测试门禁；
3. 可用的用户/项目记忆和近期报告；
4. 与当前工作和计划直接相关的新技术、新产品路径或 AI Native 理念。

若候选依赖时效性强的新理念，先从官方文档、原始论文或项目一手资料核对；不为追求“新”而加入与当前路径无关的概念。记忆中的时效性事实需重新验证。

## 表达格式

```markdown
### 明日/下周尝试候选

- **A. ……（推荐）**：在……环节……。适合现在，因为……。最小验收：……。
- **B. ……**：在……环节……。适合现在，因为……。最小验收：……。
- **C. ……**：在……环节……。适合现在，因为……。最小验收：……。

推荐 A。你想采用 A/B/C、保持当前草稿，还是直接修改某段？
```

## 终止条件

- `确认提交`、`确认发布`、`可以发`、`发布到推推`、`确认回帖`：立即发布当前最后展示的版本，停止反问。
- `不发布`、`先保存`：停止交互，不执行外部写入。
- `不添加建议`：移除明日/下周尝试章节，展示最终稿后等待确认；不要劝用户保留。
- 发布失败：只报告工具错误和可执行的下一步；不得用新的内容问题转移失败。
